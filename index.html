Robot learning middleware

Turn every robot arm in your lab into a URL.

n-droids decouples robot hardware from AI inference. r2d2 is a container that lives next to the arm and owns every driver. c3po is a three-dependency Python client you install anywhere. Teleop, data collection, replay and policy rollouts become the same ten-line loop.

Every lab rebuilds the same plumbing

Three costs show up in every robot learning group, and none of them are the research.

Driver and version hell

libfranka versions are pinned to robot firmware. The ZED SDK wants CUDA; RealSense wants its own runtime; every motor bus wants a different serial driver. Each new laptop becomes a snowflake nobody can reproduce.

One machine holds the robot

The workstation with the drivers, the real-time kernel and the calibration is a single point of contention. One person uses the arm at a time, and nobody can bring their own environment to it.

Every experiment is bespoke

Teleop, demonstrations, replay and policy rollouts end up as four unrelated scripts that each talk to the hardware slightly differently — so results are hard to compare and code is hard to hand to the next student.

Two halves, one boundary

Hardware lives on the station. Research code lives on your machine. They meet at a single WebSocket and a machine-readable manifest.

r2d2 owns the hardware

It runs LeRobot's robot, camera and teleoperator classes, plus plugins for the hardware LeRobot doesn't ship. It never runs a policy. Joint state goes out as JSON text frames; camera pixels go out as binary frames — no base64, no JSON wrapping.

c3po owns the experiment

A single Robot object with reset() and step(action). The station owns the loop cadence, so step() blocks until the next observation arrives and your loop is naturally paced at the station's rate.

What you get

Design decisions that remove configuration rather than add it.

One API, any station

On connect, the client asks the station to describe itself and derives every observation and action key from the reply. Single arm, bimanual, one camera or three — the same script runs unmodified.

A client that installs anywhere

numpy, Pillow, websocket-client. No CUDA, no ROS, no robot drivers, no real-time kernel, no Docker on your laptop.

Recording that survives you

Data is written on the station, not the client. A crashed policy loop doesn't cost you the episode, and finished datasets come back over the same Ethernet cable.

Teleop devices are sensors

Leader arms, gamepads and keyboards appear in the observation dictionary next to the follower. The protocol treats them identically — mimicry data collection is just a dictionary lookup.

Hardware by plugin

Machines LeRobot doesn't ship are ordinary lerobot_robot_* and lerobot_camera_* packages. Adding an arm is one plugin and one YAML file, not a fork.

Introspection built in

robot.spec() reports the effective control rate, camera FPS and recording state. Lifecycle events — episode boundaries, watchdog trips, rejected actions — stream back as status messages.

Design notes

Three choices worth knowing before you adopt it.

Built on LeRobot, not instead of it

r2d2 imports LeRobot's hardware layer rather than reimplementing motor buses and camera drivers, and vendors it torch-free. n-droids adds the parts LeRobot doesn't ship: a station protocol, server-side recording, and teleop devices exposed as sensors.

No ROS 2, no DDS

The station is a setpoint relay. Each arm's own controller keeps its safety reflexes and its real-time loop; the station never replaces them. One WebSocket carries everything.

MDP-shaped, not Gym-shaped

reset() and step() are there and the station owns the cadence, but this is not a gym.Env: there are no spaces, no seeding, and reward/done are dataset metadata rather than RL semantics.
