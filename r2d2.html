Overview/Station

Setting up an r2d2 station

One small computer next to the robot, one Docker container, one YAML file. You do this once per arm — after that, everyone in the lab just connects to it.

What you are building

r2d2 runs on the machine physically wired to the robot — a NUC, a mini-PC, any Linux box on the same bench. It owns the motor buses, the cameras, the teleop devices and the dataset writer. It never runs a policy, and it exposes everything through one WebSocket on port 9090 plus an HTTP endpoint on 9091 for pulling datasets off.

  • webSocketPort 9090 — control, joint state, camera frames.
  • httpPort 9091 — serves finished datasets for download.
  • configOne YAML file, mounted at /config/station.yaml.
  • storageDatasets land in /datasets on the station.
  • entrypointr2d2-server --config /config/station.yaml
i

Hardware safety stays where it belongs. The station relays setpoints. Each arm's own controller keeps its real-time loop, its force limits and its reflexes, and the physical e-stop remains the stop mechanism. Running r2d2 does not require a real-time kernel — the exception is a Franka Panda, whose FCI link does.

Prerequisites

  • Ubuntu or Debian on the station host, with Docker installed and your user in the docker group.
  • The robot and its cameras attached by USB or Ethernet, powered, and in a safe state.
  • An Ethernet cable to the machine that will run your code.
  • Roughly 1 GB of disk for the image, plus room for datasets.

A Franka Panda station needs more — a PREEMPT_RT kernel, the ZED SDK, CUDA and the NVIDIA Container Toolkit. See the Franka section.

Setup

  1. Put both machines on the same subnet

    The station takes 10.42.0.1 and your client machine takes 10.42.0.2. These are private addresses on a cable that carries nothing else.

    on the station
    sudo ip addr add 10.42.0.1/24 dev <station-interface>
    on the client machine
    sudo ip addr add 10.42.0.2/24 dev <client-interface>

    Verify from the client with ping 10.42.0.1. The addresses are lost on reboot unless you persist them with netplan or NetworkManager — see the network guide.

  2. Build the image

    The build clones LeRobot v0.6.0, applies two patches that make it torch-optional, and installs the hardware plugins. Nothing CUDA-related is baked in.

    on the station
    git clone https://github.com/kaolab-research/r2d2.git
cd r2d2
docker build -t r2d2:latest .

  3. Find your device paths

    /dev/ttyACM0 and /dev/video0 are assigned in enumeration order and will swap across reboots. Use the by-path symlinks instead — they are tied to physical USB ports, and they work even for cameras with no serial number.

    on the station
    ls -l /dev/serial/by-path/    # arms, leaders, serial grippers
ls -l /dev/v4l/by-path/       # UVC cameras

    Unplug a device and re-run the command to identify which symlink belongs to which device — the one that disappears is the one you want.

  4. Write the station config

    The YAML maps almost one-to-one onto LeRobot's config dataclasses. Copy one of the ready-made files in config/ and edit the paths.

    config/station.so101.yaml
    station_model: so101_teleop      # identifier reported to clients

robot:
  type: so_follower              # -> LeRobot SOFollower
  id: my_follower_arm            # matches the calibration file name
  port: /dev/serial/by-path/pci-0000:00:14.0-usb-0:7:1.0
  baudrate: 1000000
  cameras:
    front_rgb:
      type: opencv               # -> LeRobot OpenCVCamera
      index_or_path: /dev/v4l/by-path/pci-0000:00:14.0-usb-0:14:1.0-video-index0
      width: 640
      height: 480
      fps: 30

teleop:
  type: so_leader                # the leader arm appears as a controller
  id: my_leader_arm
  port: /dev/serial/by-path/pci-0000:00:14.0-usb-0:6:1.0
  baudrate: 1000000
    ✓

    No teleop device? Drop the teleop: block — a station with only a follower is valid, and a client can command it directly.

  5. Launch it

    Each config has a matching launch script that handles device passthrough, the calibration mount and the dataset volume.

    on the station
    ./launch_scripts/so101_uvc.sh
docker logs -f r2d2-so101-uvc

    Available scripts:

    • toy.sh — synthetic station, no hardware at all
    • so101_uvc.sh · so101_dual_uvc.sh · so101_all_cams.sh · so101_realsense.sh · so101_nocam.sh
    • rebot_bimanual_2realsense.sh · rebot_bimanual_3realsense.sh · rebot_bimanual_nocam.sh
    • droid.sh — Franka Panda + Robotiq + 2× ZED

  6. Verify

    From the client machine, confirm the handshake and read back the manifest:

    on the client machine
    from c3po import Robot

with Robot(host="10.42.0.1") as robot:
    print(robot.station_model, robot.arms, robot.cameras, robot.controllers)
    print(robot.spec())

    If that prints your station, you are done. Anyone with the cable and c3po installed can now use the arm.

Calibration

The station connects with calibrate=False — it expects a calibration file to already exist and mounts it from the host:

docker run
-v ~/.cache/huggingface/lerobot/calibration:/root/.cache/huggingface/lerobot/calibration

The value of id: in your station config (for example my_follower_arm) must match the calibration file for that arm. Calibrate once using LeRobot's own tooling on the host, and every client thereafter inherits it.

Development without hardware

Toy mode publishes synthetic joint states and camera frames, so you can write and test client code with no robot connected:

shell
./launch_scripts/toy.sh

# or directly, on any machine:
r2d2-server --toy
!

Use the r2d2-server command, not python -m r2d2._server. The module has no __main__ guard, so running it as a module exits silently without starting anything. The console script is the supported entry point.

Franka Panda station

The droid station — Panda + Robotiq 2F-85 + two ZED cameras — is the one configuration with real host requirements, because the FCI link is genuinely real-time and the ZED SDK needs the GPU stack.

  • PREEMPT_RT kernel: sudo pro enable realtime-kernel
  • A realtime group, with your user in it, and raised rtprio/memlock limits
  • Stereolabs ZED SDK installed on the host
  • CUDA installed on the host — the ZED SDK links against the CUDA runtime
  • NVIDIA Container Toolkit, so --gpus all can supply the driver libraries
  • Franka Desk: joints unlocked and FCI mode active

The launch script mounts the host's ZED libraries, CUDA runtime and SDK settings, and runs the container with --network=host --privileged --gpus all. The Python bindings for ZED are baked into the image, version-matched to the host SDK through a build argument:

shell
docker build -t r2d2:latest --build-arg ZED_SDK_VERSION=5.4.1 .
./launch_scripts/droid.sh

The arm itself is driven by a C++ shim holding the 1 kHz FCI torque loop over shared memory, with a Python loop computing torque from targets the driver writes at the policy rate. DROID actions are joint velocities plus a gripper position, and the station is pinned to 15 Hz.

Full host instructions, including the real-time kernel and Desk configuration, are in franka_setup.md.

Adding hardware LeRobot doesn't support

Anything upstream doesn't ship is an ordinary plugin package — no changes to the server, the protocol or the manifest. It is discovered through LeRobot's own plugin mechanism.

layout
plugins/lerobot_robot_myarm/
├── pyproject.toml                  # name must start with lerobot_robot_
└── src/lerobot_robot_myarm/
    ├── __init__.py                 # exports the driver
    ├── config_myarm.py             # RobotConfig subclass
    └── myarm.py                    # Robot subclass
  1. The dist name starts with lerobot_robot_ or lerobot_camera_.
  2. The config class is decorated with @RobotConfig.register_subclass("myarm").
  3. The driver class is named after the config with Config stripped.
  4. Both are exported from the package's __init__.py.

Then reference it from station.yaml with type: myarm. Everything else — manifest, recording, watchdog, cameras — works unchanged.

Running the tests

The suite runs against the toy station and covers the protocol, streaming, recording and spec/status messages end to end. Hardware backends are exercised through fakes, so it runs anywhere:

shell
cd r2d2
uv run pytest

Plugin suites live alongside their packages: plugins/lerobot_robot_franka and plugins/lerobot_camera_zed.

The compatibility boundary

Clients and stations are versioned independently. The contract between them is the manifest returned by a describe request, carrying an api_version — any client with the same major version can talk to any station.

Channel Format Carries
Text frames JSON describe, observations, actions, recording commands, status events
Binary frames Header + raw pixels Camera images — RGB as uint8, depth as uint16
HTTP :9091 Static files Finished datasets — metadata, parquet, video

Troubleshooting

Symptom What to check
Client can't reach the station ping 10.42.0.1. If that fails, the static IPs aren't set — they do not survive a reboot unless persisted.
Arm doesn't move, logs look empty Check docker logs for the control rate actually achieved, and robot.spec() from the client for overruns.
Camera declared but no frames arrive The by-path symlink changed because a cable moved to a different USB port. Re-run ls -l /dev/v4l/by-path/.
Devices swap between reboots You are using /dev/ttyACM* or /dev/video* instead of the by-path symlinks.
Calibration not found The station's id: doesn't match the calibration file name, or the calibration directory isn't mounted.
ZED fails with libcuda.so.1: cannot open shared object file The NVIDIA Container Toolkit isn't installed, so --gpus all has nothing to pass through.
